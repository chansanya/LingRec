# LingRecSys 灵荐推荐系统 V1 运行说明

版本：v1.0.0
日期：2026-09-21
更新日期：2026-09-22
适用范围：LingRecSys V1 推荐系统 Demo

---

## 一、系统整体结构

LingRecSys 由四个部分组成：浏览器操作面板、Spring Boot 推荐服务、MySQL 数据存储和 Python FastAPI 算法服务。

```text
浏览器操作面板
       │
       │ HTTP API
       ▼
Spring Boot 推荐服务
       │
       ├── MySQL
       │   ├── 用户
       │   ├── 分类
       │   ├── 资源
       │   ├── 用户行为
       │   └── 用户画像
       │
       └── HTTP POST
               │
               ▼
        Python FastAPI
        召回 + 排序算法
               │
               ▼
          推荐资源 ID
               │
               ▼
Spring Boot 组装资源详情
               │
               ▼
浏览器展示推荐结果
```

Python 服务是无状态计算服务：

- 不连接 MySQL；
- 不保存用户画像；
- 不保存推荐结果；
- 每次由 Java 传入用户画像和候选资源；
- 只返回资源 ID 推荐顺序。

## 二、系统启动时做什么

Spring Boot 启动后，`DataGenerator` 检查 MySQL 中用户、分类和资源数据是否完整。

数据库为空时生成：

- 5 个资源大类；
- 20 个资源小类；
- 200 条资源；
- 10 个模拟用户；
- 约 540～720 条模拟行为。

分类结构示例：

```text
游戏
├── FPS
├── RPG
├── MOBA
└── SLG

编程
├── Java
├── Python
├── Go
└── JavaScript
```

资源关联到小类，例如：

```text
CS2 竞技技巧教程
categoryId = FPS
```

模拟用户兴趣定位：

| 用户 | 主要兴趣 |
|---|---|
| 游戏达人小明 | 游戏 |
| 程序员老张 | 编程 |
| 设计师小美 | 设计 |
| 音乐发烧友 | 音乐 |
| 影视达人 | 影视 |
| 全能学霸 | 随机分布 |
| 游戏+编程 | 游戏、编程 |
| 文艺青年 | 设计、音乐 |
| 技术宅 | 编程、游戏 |
| 新用户小白 | 无行为，用于冷启动 |

前 9 个用户生成行为，第 10 个用户无行为，用于冷启动演示。

资源初始热度为 10～500，发布时间随机分布在过去 90 天。

## 三、用户打开页面后发生什么

前端并行请求：

```text
GET /api/categories
GET /api/users
```

取得用户列表后，默认选择第一个用户，并继续请求：

```text
GET /api/recommend/{userId}
GET /api/users/{userId}/profile
GET /api/behaviors/{userId}?limit=20
```

页面初始展示：

### 1. 用户信息

来自 `users` 表：

- 昵称；
- 头像图标；
- 创建时间。

### 2. 行为统计

统计当前用户全部历史行为：

```text
VIEW 浏览次数
LIKE 点赞次数
FAVORITE 收藏次数
```

这不是最近 20 条的统计。

### 3. 兴趣画像

来自 `user_profile`，按资源小类展示兴趣分，例如：

```text
RPG        100
SLG         79.1
FPS         58.1
MOBA        55.8
Java        20.9
```

画像按小类计算，不按大类计算。

### 4. 行为记录

行为记录使用一个固定面板，通过浏览、点赞、收藏三个标签点击切换；每个标签展示对应类型最近 20 条记录，包含：

```text
行为类型
资源名称
大类 / 小类
发生时间
```

### 5. 推荐资源

推荐采用有界候选召回 + Redis 快照 + 游标分页：

1. 服务端从 MySQL 召回有限候选池，避免全表加载；
2. Python 对候选池排序，排序结果保存为 Redis 推荐会话；
3. 首次请求返回第一页（默认 20 条）；
4. 滚动到底部时按 sessionId 和 cursor 请求下一页；
5. 整个会话内排序稳定且资源不重复。

每张资源卡片展示：

- 封面；
- 标题；
- 大类 / 小类；
- 描述；
- 热度；
- 浏览、点赞、收藏按钮。

## 四、分类筛选如何影响推荐

操作面板有三种候选范围。

### 1. 全部

不传 `categoryId`，Java 查询全部资源。

### 2. 大类

选择“游戏”时，Java 查询游戏大类下全部小类资源：

```text
FPS
RPG
MOBA
SLG
```

Python 收到的候选集只包含游戏资源。

### 3. 小类

选择 FPS 时，Java 只查询：

```text
category_id = FPS ID
```

分类过滤优先于用户画像。即使用户最喜欢 Java，选择 FPS 后也只会返回 FPS 资源。

## 五、用户点击资源后发生什么

系统支持三类行为：

```text
VIEW      浏览，权重 1
LIKE      点赞，权重 3
FAVORITE  收藏，权重 5
```

触发方式：

- 点击整张资源卡片：记录 `VIEW`；
- 点击浏览按钮：记录 `VIEW`；
- 点击点赞按钮：记录 `LIKE`；
- 点击收藏按钮：记录 `FAVORITE`。

按钮区域使用 `@click.stop`，避免按钮行为额外触发卡片浏览。

前端提交：

```http
POST /api/behaviors
Content-Type: application/json
```

请求体：

```json
{
  "userId": 1,
  "resourceId": 35,
  "action": "FAVORITE"
}
```

## 六、行为写入后 Java 做了什么

行为服务按以下顺序执行。

### 1. 校验用户和资源

检查：

- 用户是否存在；
- 资源是否存在；
- 行为是否属于 `VIEW`、`LIKE`、`FAVORITE`。

非法行为，例如：

```json
{
  "action": "BUY"
}
```

直接返回 `400`，不会写库。

### 2. 写入用户行为

写入 `user_behavior`：

```text
user_id
resource_id
action
created_at
```

### 3. 增加资源热度

行为权重累加到资源热度：

```text
原热度 300

浏览后 301
点赞后 303
收藏后 305
```

热度是全局属性。某个用户收藏资源后，该资源对其他用户的热门程度也会提高。

### 4. 重新计算当前用户画像

普通页面行为会立即读取该用户全部行为并重算画像。

数据生成器使用不带画像刷新的写入方法，最后每个用户只重算一次，避免生成期间重复全量计算。

---

## 七、用户画像具体如何计算

画像按资源小类聚合，计算分两步。

### 第一步：计算小类原始分

```text
分类原始分 = 该分类下所有行为权重之和
```

示例：

```text
浏览 FPS 2 次
点赞 RPG 1 次
收藏 Java 1 次
```

权重：

```text
VIEW = 1
LIKE = 3
FAVORITE = 5
```

原始分：

```text
FPS  = 2 × 1 = 2
RPG  = 1 × 3 = 3
Java = 1 × 5 = 5
```

### 第二步：归一化到 0～100

公式：

```text
最终兴趣分 = 当前分类原始分 / 当前用户最高分类原始分 × 100
```

最高分为 Java 的 5：

```text
FPS  = 2 / 5 × 100 = 40
RPG  = 3 / 5 × 100 = 60
Java = 5 / 5 × 100 = 100
```

结果：

```json
[
  { "categoryName": "FPS", "score": 40 },
  { "categoryName": "RPG", "score": 60 },
  { "categoryName": "Java", "score": 100 }
]
```

## 八、一次点击为什么可能改变所有画像分数

假设画像为：

```text
FPS  原始分 2 → 40
RPG  原始分 3 → 60
Java 原始分 5 → 100
```

用户收藏一个 FPS 资源：

```text
FPS 原始分 +5
```

新的原始分：

```text
FPS  = 7
RPG  = 3
Java = 5
```

最高分变为 FPS 的 7，归一化结果：

```text
FPS  = 7 / 7 × 100 = 100
RPG  = 3 / 7 × 100 = 42.86
Java = 5 / 7 × 100 = 71.43
```

一次点击后：

```text
FPS：40 → 100
RPG：60 → 42.86
Java：100 → 71.43
```

RPG 和 Java 的兴趣没有减少，图表展示的是当前用户内部各兴趣的相对强弱，不是绝对兴趣值。

---

## 九、行为完成后页面为什么马上变化

行为提交成功后，前端并行刷新：

```text
用户画像
行为记录
（当前分类推荐不会自动刷新）
```

因此操作后立即看到：

- 行为统计增加；
- 浏览、点赞、收藏对应标签页出现新记录；
- 画像变化。

前端使用请求序号防止旧响应覆盖新状态。

例如用户从 A 快速切换到 B：

```text
A 请求较慢
B 请求先完成
A 请求后完成
```

A 的旧响应不会覆盖 B 的页面数据。

## 十、Java 如何调用 Python

Java 取得：

1. 当前用户画像；
2. 当前分类范围内的候选资源。

组织请求：

```json
{
  "userId": 1,
  "userProfile": [
    {
      "categoryId": 2,
      "categoryName": "FPS",
      "score": 100
    },
    {
      "categoryId": 3,
      "categoryName": "RPG",
      "score": 62.5
    }
  ],
  "candidates": [
    {
      "id": 10,
      "title": "CS2 竞技技巧教程",
      "categoryId": 2,
      "categoryName": "FPS",
      "heat": 431,
      "createdAt": "2026-08-20T10:30:00"
    }
  ]
}
```

Java 同步调用：

```http
POST http://localhost:8000/recommend
```

Python 返回：

```json
{
  "resourceIds": [10, 15, 3, 20],
  "strategy": "personalized"
}
```

Python 只返回资源 ID，不返回完整资源信息。Java 根据候选资源 Map 还原详情，并保持 Python 返回顺序。

## 十一、Python 推荐算法

Python 流程：

```text
候选集检查
→ 冷启动判断
→ 多路召回
→ 综合排序
→ 返回完整排序序列
```

### 1. 空候选集

候选资源为空时返回：

```json
{
  "resourceIds": [],
  "strategy": "empty_candidates"
}
```

### 2. 冷启动

用户没有画像时按候选资源热度降序返回完整排序序列，前端再增量展示，策略为：

```text
cold_start_hot
```

---

## 十二、个性化推荐召回阶段

有画像时执行三路召回。

### 1. 兴趣召回

取用户画像分数最高的 5 个小类，召回候选集中属于这些分类的资源。

### 2. 热门召回

在当前候选集中按热度取前 30 条。

热门召回受分类过滤限制。选择“编程”后，不会召回游戏、音乐或影视资源。

### 3. 探索召回

从非主要兴趣分类中随机抽取最多 10 条，用于避免推荐完全困在既有兴趣内。

三路召回结果合并去重：

```text
兴趣召回
→ 热门召回
→ 探索召回
```

---

## 十三、Python 排序规则

综合排序权重：

```text
兴趣匹配：0.40
资源热度：0.25
资源新鲜度：0.20
多样性惩罚：0.15
```

公式：

```text
最终分 =
0.40 × 兴趣匹配度
+ 0.25 × 热度
+ 0.20 × 新鲜度
- 0.15 × 多样性惩罚
```

### 1. 兴趣匹配度

```text
资源所属分类画像分 / 用户最高画像分
```

画像最高分通常为 100，可近似理解为：

```text
兴趣匹配度 = 分类画像分 / 100
```

### 2. 热度

```text
资源热度 / 当前召回结果最高热度
```

### 3. 新鲜度

```text
新鲜度 = 1 / (1 + 资源天数 / 30)
```

大致效果：

```text
今天发布：1.0
30 天前：0.5
60 天前：约 0.33
很久以前：最低 0.1
```

### 4. 多样性惩罚

同一小类资源出现越多，后续资源惩罚越高：

```text
第一条：0
第二条：0.1
第三条：0.2
...
最高：0.5
```

最终按综合分降序，返回当前候选池的完整排序序列；该序列保存为 Redis 快照，前端按页读取。

## 十四、点击后如何影响下一轮推荐

一次点击影响两个指标。

### 影响一：用户兴趣

例如收藏 FPS：

```text
FPS 原始兴趣分 +5
```

下一轮：

```text
FPS 兴趣匹配度提高
FPS 资源整体排序上升
```

### 影响二：资源热度

被收藏的具体资源：

```text
heat +5
```

下一轮：

```text
该资源热度分提高
自身更容易排在前面
```

因此收藏一个 FPS 资源会产生双重影响：

```text
FPS 分类更符合用户兴趣
+
该资源全局热度上升
```

当前算法不排除已交互资源，刚点击的资源仍可能再次被推荐，且热度提高后排名可能更靠前。

## 十五、Python 服务不可用时

Python 未启动、端口不可访问、计算错误或请求超时时，Java 不会让页面直接失败。

降级逻辑：

```text
当前候选资源按 heat 降序
→ 返回当前候选池完整排序序列
→ 存入 Redis 推荐快照
→ 前端按 sessionId 和 cursor 分页读取
```

降级同样遵守分类范围。选择 FPS 时，即使算法服务不可用，也只返回 FPS 热门资源，不会混入其他分类。

---

## 十六、当前系统不具备的推荐能力

V1 已形成推荐闭环，但不包含以下能力。

### 1. 没有内容语义画像

当前 Python 不分析：

- 标题文本；
- 描述语义；
- 封面图片；
- 关键词；
- Embedding；
- 内容相似度。

资源特征主要是：

```text
categoryId
heat
createdAt
```

### 2. 没有协同过滤

不计算相似用户偏好。不同用户之间的行为只通过全局资源热度间接产生影响。

### 3. 没有曝光数据

系统记录点击、点赞、收藏，但不记录：

- 用户看到哪些资源；
- 推荐位顺序；
- 推荐策略；
- 用户看了但未点击的资源。

因此不能准确计算推荐点击率。

### 4. 没有兴趣时间衰减

一年前的收藏和今天的收藏在画像中权重相同。

### 5. 重复行为会重复累计

连续收藏同一资源两次，会记录两条 `FAVORITE`：

```text
画像 +5 +5
热度 +5 +5
```

当前没有收藏状态与取消收藏逻辑。

### 6. 按钮高亮只参考最近 20 条

页面按钮是否高亮检查对应行为标签页的最近 20 条记录。如果收藏记录排到第 21 条之后，按钮可能显示未收藏，但数据库仍保留历史记录。

## 十七、完整的一次点击流程

以“用户收藏一个 FPS 资源”为例：

```text
1. 用户点击收藏按钮
   ↓
2. Vue POST /api/behaviors
   action = FAVORITE
   ↓
3. Spring Boot 校验用户、资源、行为
   ↓
4. MySQL 插入 user_behavior
   ↓
5. 该资源 heat +5
   ↓
6. 重新汇总用户全部行为
   ↓
7. FPS 原始兴趣分 +5
   ↓
8. 所有分类重新归一化到 0～100
   ↓
9. user_profile 删除旧画像并写入新画像
   ↓
10. 前端重新请求画像、行为、推荐
   ↓
11. Java 查询当前分类候选资源
   ↓
12. Java 把画像和候选资源 POST 给 Python
   ↓
13. Python 执行兴趣召回、热门召回、探索召回
   ↓
14. Python 计算兴趣、热度、新鲜度、多样性分
   ↓
15. Python 返回排序后的完整资源 ID
   ↓
16. Java 组装资源详情
   ↓
17. 页面更新行为统计、兴趣图表和行为记录，推荐列表保持不变
```

## 附：推荐会话与游标分页

V1 中点击资源卡片、点赞或收藏后，页面仅更新：

- 行为统计；
- 可点击切换的浏览、点赞、收藏行为标签页；
- 兴趣画像。

此时不重新创建推荐会话。用户点击“刷新推荐”按钮时，系统才重新召回候选、调用 Python 并创建新的 Redis 推荐会话。

推荐会话流程：

1. 服务端从 MySQL 召回有界候选池；
2. Python 对候选池排序并去重；
3. 排序后的资源 ID 保存为 Redis 快照，并生成 sessionId；
4. 首次返回第一页（默认 20 条）；
5. 用户滚动到资源面板底部附近时，按 sessionId 和 cursor 请求下一页；
6. 整个会话内排序稳定、资源不重复、不写入用户行为；
7. 快照过期后需要重新创建推荐会话。

分页读取只是用户继续查看同一轮推荐结果，不等同于刷新推荐，也不会产生 `VIEW`、`LIKE` 或 `FAVORITE` 行为。
